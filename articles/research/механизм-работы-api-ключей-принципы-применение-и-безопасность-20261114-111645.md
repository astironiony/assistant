## Введение  
API‑ключ (англ. *API key*) — уникальная строка, выдаваемая разработчиком сервиса клиенту для идентификации и (часто) авторизации при обращении к программному интерфейсу. Ключи позволяют автоматизировать доступ к ресурсам без необходимости интерактивного ввода логина и пароля, упрощая интеграцию сторонних приложений, мобильных клиентов и скриптов.

## История появления  

| Период | Событие |
|--------|---------|
| Конец 1990‑х гг. | Первые веб‑службы (SOAP, XML‑RPC) используют простые токены для идентификации клиента. |
| 2000‑е годы | Распространение REST‑архитектуры приводит к широкому внедрению коротких строк‑ключей в публичных API (Google Maps, Amazon S3). |
| 2010‑е годы | Появление облачных платформ (AWS, Azure, GCP) формализует управление ключами, вводя роли, ограничения по времени и области действия. |
| Современный этап | Интеграция с системами управления секретами (HashiCorp Vault, AWS Secrets Manager) и применение «скоуп‑ключей» для минимизации прав доступа. |

## Принцип действия  

### 1. Генерация  
* Сервис генерирует случайную последовательность символов (обычно 32‑256 бит энтропии), кодируя её в Base64, Hex или UUID‑формате.  
* При генерации могут учитываться метаданные: идентификатор пользователя, срок действия, список разрешённых операций (scopes).

### 2. Хранение  
* **На стороне сервера**: ключ хранится в защищённой базе (обычно в виде хеша, аналогично паролю) — например, `SHA‑256(key)`. Хеш позволяет сравнивать без раскрытия самого ключа.  
* **На стороне клиента**: ключ помещается в переменные окружения, файлы конфигурации с ограниченными правами доступа или в специальные хранилища секретов.

### 3. Передача в запросе  
Ключ включается в HTTP‑запрос одним из стандартных способов:  

| Способ | Пример |
|--------|--------|
| Заголовок `Authorization` | `Authorization: ApiKey 12345abcdef` |
| Параметр URL‑строки | `https://api.example.com/resource?api_key=12345abcdef` |
| Тело запроса (JSON) | `{ "api_key": "12345abcdef" }` |

### 4. Проверка на сервере  
1. Сервер извлекает ключ из запроса.  
2. Вычисляет хеш полученного значения.  
3. Сравнивает хеш с записью в базе.  
4. При совпадении проверяет дополнительные ограничения (срок, scopes, IP‑фильтры).  
5. Если все проверки пройдены, запрос считается аутентифицированным; иначе — отклоняется с кодом `401 Unauthorized` или `403 Forbidden`.

### 5. Обновление и отзыв  
* **Ротация** — регулярная замена ключа (например, раз в 90 дней) для снижения риска компрометации.  
* **Отзыв** — удаление или деактивация ключа в базе; клиент получает ошибку при следующем запросе.

## Типы и варианты API‑ключей  

| Вид | Характеристика | Применение |
|-----|----------------|------------|
| **Простой (static) ключ** | Фиксированная строка, без ограничения срока. | Быстрый прототип, публичные сервисы с низким уровнем риска. |
| **Scoped key** | Содержит список разрешённых операций (read, write, admin). | Ограничение прав доступа для отдельных микросервисов. |
| **Временный токен** | Имеет ограниченный TTL (например, 1 час). Выдаётся после аутентификации пользователя. | Замена пароля в мобильных приложениях, защита от кражи ключа. |
| **IP‑привязанный ключ** | Доступ разрешён только с указанных IP‑адресов/подсетей. | Защита сервер‑к‑серверу, корпоративные интеграции. |

## Сравнение с другими методами аутентификации  

```markdown
| Метод               | Требует пользовательского ввода | Поддерживает ограничение прав | Подходит для машинного доступа | Требует отдельного сервера токенов |
|---------------------|----------------------------------|-------------------------------|--------------------------------|------------------------------------|
| API‑ключ            | Нет                              | Да (scopes, IP)               | Да                             | Нет                               |
| OAuth 2.0 (access token) | Частично (для получения токена) | Да (scopes)                   | Да                             | Да (authorization server)         |
| HTTP Basic Auth     | Да (логин/пароль)                | Нет                           | Да (при хранении в конфиге)    | Нет                               |
| JWT (JSON Web Token) | Нет (если токен уже получен)    | Да (claims)                   | Да                             | Да (если используется refresh‑token) |
```

## Пример реализации проверки API‑ключа (Node.js + Express)

```javascript
// server.js
const express = require('express');
const crypto = require('crypto');
const app = express();

// Пример хранилища: { hash: '...', scopes: ['read', 'write'], expiresAt: Date }
const apiKeyStore = new Map();

/* Функция для создания нового ключа */
function generateApiKey(scopes = [], ttlMs = 30 * 24 * 60 * 60 * 1000) {
  const rawKey = crypto.randomBytes(32).toString('hex'); // 64‑символьный ключ
  const hash = crypto.createHash('sha256').update(rawKey).digest('hex');
  const record = {
    hash,
    scopes,
    expiresAt: new Date(Date.now() + ttlMs),
  };
  apiKeyStore.set(hash, record);
  return rawKey; // отдаём клиенту только raw‑key
}

/* Middleware для проверки ключа */
function apiKeyAuth(requiredScope) {
  return (req, res, next) => {
    const key = req.header('Authorization')?.replace(/^ApiKey\s+/i, '') ||
                req.query.api_key;
    if (!key) return res.status(401).json({ error: 'Missing API key' });

    const hash = crypto.createHash('sha256').update(key).digest('hex');
    const record = apiKeyStore.get(hash);
    if (!record) return res.status(403).json({ error: 'Invalid API key' });

    if (record.expiresAt < new Date())
      return res.status(403).json({ error: 'API key expired' });

    if (requiredScope && !record.scopes.includes(requiredScope))
      return res.status(403).json({ error: 'Insufficient scope' });

    // При необходимости можно добавить req.apiKey = record;
    next();
  };
}

/* Пример защищённого эндпоинта */
app.get('/data', apiKeyAuth('read'), (req, res) => {
  res.json({ data: 'Secure information' });
});

/* Запуск сервера */
app.listen(3000, () => console.log('API listening on :3000'));
```

## Практические рекомендации по безопасности  

1. **Хешировать ключи** в базе, а не хранить их в открытом виде.  
2. **Ограничивать права** (scopes) и срок действия, особенно для публичных интеграций.  
3. **Использовать HTTPS** — без шифрования ключ может быть перехвачен в пути.  
4. **Регулярно ротировать** ключи и поддерживать журнал их выдачи/отзыва.  
5. **Не включать ключ в URL‑строку** в публичных журналах и браузерных историях; предпочтительно заголовок.  
6. **Контролировать доступ к хранилищу** клиентского ключа (например, переменные окружения с правами `0600`).  
7. **Внедрять мониторинг**: отслеживание аномального количества запросов от одного ключа.

## Интересные факты  

* Некоторые крупные облачные провайдеры (AWS, GCP) позволяют создавать **ключи‑субпользователи**, каждый из которых имеет отдельный набор прав, что упрощает аудит и автоматизацию.  
* В ранних версиях Google Maps API ключи использовались **только для отслеживания использования**; позже к ним добавили ограничения по рефереру и IP‑адресу.  
* При работе с **IoT‑устройствами** часто применяют «привязанные к устройству» API‑ключи, которые хранятся в защищённом элементе (TPM, Secure Enclave).

## Заключение  
API‑ключи представляют собой простой, но мощный механизм аутентификации машинных клиентов. Их работа основана на генерации случайных токенов, безопасном хранении (обычно в виде хеша) и проверке при каждом запросе. При правильном использовании — ограничении прав, ротации и защите передачи — API‑ключи обеспечивают достаточный уровень безопасности для большинства публичных и внутренних сервисов. Однако в сценариях, требующих более гибкой авторизации (делегирование прав, пользовательская аутентификация), рекомендуется комбинировать ключи с протоколами OAuth 2.0 или JWT. Правильный баланс между удобством и защитой делает API‑ключи незаменимым элементом современной экосистемы веб‑служб.  

```mermaid
flowchart TD
    A[Клиент] -->|Отправка запроса с API‑ключом| B[Веб‑сервер]
    B --> C{Извлечь ключ}
    C -->|Ключ найден| D[Вычислить хеш]
    D --> E{Сравнить с записью в БД}
    E -->|Хеш совпадает| F[Проверить ограничения (scope, IP, TTL)]
    F -->|Все проверки пройдены| G[Обработать запрос]
    G --> H[Ответ клиенту]
    E -->|Хеш не совпадает| I[Отказать: 403]
    F -->|Ограничения не выполнены| I
```
